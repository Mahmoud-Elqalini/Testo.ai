# Testo Constitution

## Core Principles

### I. The Server Is the Sole Source of Truth
The client (browser, mobile app) is never trusted to determine exam timing, exam state, or correctness of answers. The following MUST always be computed, validated, or enforced server-side, never client-side: whether an exam attempt is open, expired, or already submitted; the remaining time on an attempt (the client-side timer is a UI convenience only, never an authority); whether a submitted answer is correct/how it scores, and the resulting total score; whether an attempt token is currently valid. **Rationale:** a client can always be intercepted, its JavaScript modified, or its system clock changed — any rule enforced only in the browser is a suggestion to an adversarial user, not a rule.

### II. Zero Exposure of Grading Criteria
No grading criteria — whether an MCQ's correct-answer flag (`is_correct`) or an essay question's model answer/scoring rubric used for automated grading — MUST be queryable, readable, or transmitted to a student-facing client at any point while that student's attempt is still open. Student-facing endpoints returning exam questions MUST exclude all grading-criteria fields at the query level, not merely hide them in the UI. All comparison of a student's answer against grading criteria — whether the deterministic MCQ comparison or the automated essay evaluation (Principle X) — MUST run in server-side/trusted code only. Privileged credentials (service-role keys, admin API keys, or any credential capable of bypassing access control) MUST NEVER be embedded in frontend code or any artifact shipped to the browser. **Rationale:** hiding grading criteria in the UI while still sending it over the network, or exposing a rubric a smart student could reverse-engineer answers from, is not security; this principle prevents the single most damaging failure mode of an exam platform — for either question type.

### III. Defense in Depth for Exam Access
No single mechanism is ever relied upon alone to grant exam access. Every attempt MUST be protected by the composition of: Authentication (verified logged-in user); Authorization (row-level policies restricting each user to their own data); a unique, unguessable, time-scoped attempt token bound to one student/exam/attempt triple and valid only within the exam's actual scheduled window; and server-side time/state validation re-checked on every request, not just at token issuance. A leaked or guessed link alone MUST NEVER be sufficient to access or influence an exam. **Rationale:** each layer covers the others' potential failure.

### IV. Data Integrity and Resilience Take Priority Over Convenience
No work a student has already done may be silently lost, and no attempt may be manipulated into an inconsistent state.

- **Autosave cadence:** answers MUST be saved via a bounded, debounced event — on MCQ choice selection, or after a short pause in typing / on field blur for free-text essay answers — never on every keystroke. Write volume must scale with real activity, not typing speed.
- **Offline handling:** if the client loses connectivity, new or changed answers MUST be queued locally and the UI MUST clearly show an "unsynced" state rather than a false "saved" confirmation — an answer is only considered saved once the server acknowledges it. Any queued answer that reaches the server after the attempt's window has already been closed under Principle I MUST be rejected and MUST NOT be counted; client-side queuing is a UX convenience, never a way to extend an exam past its authoritative end time.
- **Attempt lifecycle:** every attempt MUST move through an enforced state machine: `pending` (token/attempt row exists, student has not yet opened it) → `in_progress` → one of `submitted`, `auto_submitted`, or `abandoned` (the exam window closed with no submission ever recorded). An Admin MAY move any non-`pending` attempt to `voided`, for a documented reason, recording who voided it and when — this is the only sanctioned path for correcting a technical error or an interrupted attempt, and MUST NOT be done through direct, unlogged database edits.
- An attempt whose time has expired MUST be closed and graded automatically by a server-side scheduled process — the platform MUST NOT depend on the student's browser staying open. A token or attempt MUST NOT be usable more than once.

**Rationale:** exams are high-stakes and often one-shot; a lost answer, a double-submission, or an attempt stuck in an undefined state directly harms a student's grade and the platform's credibility.

### V. Every Automated Notification Is Logged, Deduplicated, and Retried
No email or other notification is ever sent blindly. For every notification, there MUST be a persisted record of what was sent, to whom, for which event, its delivery status (pending/sent/failed), and its timestamp, with automatic bounded retry on failure using an idempotent notification identity that minimizes duplicate sends — an absolute "never duplicates" guarantee is not achievable given email transport's inherent uncertainty (e.g. a lost delivery acknowledgment can cause an honest retry to duplicate), but the system's own send *decision* MUST be idempotent and consistent. Scheduled notifications MUST be idempotent — re-running the scheduler must never re-send something already logged as sent. **Rationale:** silent failures and silent duplicates both erode trust; logging turns "we hope it worked" into something verifiable, and stating the guarantee honestly (system-side idempotency, not a transport-level impossibility) keeps the constitution technically truthful.

### VI. Cost-Conscious, Usage-Driven Scaling
The platform MUST be able to start and remain on free or near-free infrastructure tiers at initial scale (low hundreds of students) and MUST NOT be architected in a way that forces a premature paid upgrade. Any hard external limit or variable cost affecting correctness, UX, or budget — including a daily email-sending cap, and any paid inference/API cost introduced by the grading mechanism (Principle X) — MUST be actively tracked and projected per exam, and surfaced to the Admin *before* an exam is published, not discovered after failures or a bill arrive. Phase 1's local embedding inference has near-zero marginal cost per grading call; this tracking requirement exists so that if a future paid fallback (e.g. an LLM API) is introduced, it is monitored with the same discipline from day one rather than retrofitted after an unexpected bill. Upgrades to paid tiers respond to *measured* usage, never a starting assumption. **Rationale:** this is a tutoring-group project, not a funded startup; cost discipline is a real constraint, and an unmonitored limit or cost silently violates Principle V's spirit of "nothing happens blindly."

### VII. Simplicity Before Sophistication (MVP Discipline)
Features are added in order of what makes the core exam loop trustworthy first, then convenient, then insightful. The Phase 1 (MVP) grading scope explicitly includes both: single-correct-answer MCQ (no negative marking, no partial credit), and automatically-graded free-text/essay questions (Principle X) — essay support is a Phase 1 requirement, not a deferred nice-to-have. Within Phase 1, essay grading is holistic (one automatically-assigned score per question) rather than broken into sub-criteria, until a proven need for finer-grained rubrics exists. Human review is not part of the normal grading workflow; Admin review is available only as an exception after grading (Principle X's post-hoc override), never as a routine step in the pipeline itself. Notification scheduling, advanced statistics, leaderboards, certificates, AI-driven longitudinal analysis, and multi-select questions and multiple attempts per exam are all explicitly deferred to a later phase and MUST NOT block or complicate Phase 1. A feature adding architectural complexity beyond this scope MUST NOT be built "just in case" — only when a corresponding requirement exists in `spec.md`. **Rationale:** the highest-value, riskiest part of this system is a student securely and reliably getting a trustworthy grade — on either question type — on one exam; everything added before that is solid increases surface area for bugs and security gaps.

### VIII. Strict TDD for Logic; Visual Regression Testing for Presentation (NON-NEGOTIABLE)
For all behavioral/logic code — backend services, Edge Functions, database policies, grading logic (including the automated grading pipeline — embedding computation, similarity scoring, or any future prompt construction — response handling, and score parsing under Principle X), attempt state-machine transitions, and token/time validation — no implementation code is written before a failing test exists for it. The Red-Green-Refactor cycle MUST be followed: (1) **Red** — write the test(s) first, run them, confirm they fail; a test that passes before the implementation exists is invalid and must be corrected; (2) **Green** — write the minimum code necessary to pass; (3) **Refactor** — clean up without changing behavior, tests staying green throughout. Row-level security policies MUST have tests proving unauthorized access is denied, not only tests proving authorized access works.

For presentation and theming — visual layout, Dark/Light mode styling, and RTL/LTR direction handling covered by Principle IX — Red-Green-Refactor unit testing is explicitly NOT the required tool, because visual correctness is not a logic assertion and brittle pixel/color assertions catch nothing real. Instead, every themed/directional component MUST have Visual Regression Testing (automated screenshot comparison) covering at minimum its light, dark, Arabic (RTL), and English (LTR) renderings, with a visual diff reviewed before merge. This substitution is strictly scoped to presentation/styling — any interactive logic inside such a component (form validation, state transitions, data fetching) remains fully governed by Red-Green-Refactor like any other logic code.

A task is not "done" if logic tests were written after the implementation, or written and passed in the same pass without ever failing first. Coverage gaps found later (e.g. via `/speckit.analyze`) MUST be closed by writing the missing failing test first, then the fix.

**Rationale:** for an exam platform the cost of an undetected logic regression is a leaked grading criterion, a wrongly graded student, or a security policy that silently stopped enforcing itself — writing the test first forces correct behavior to be proven capable of failing. Presentation code has different failure modes (it "looks wrong," it doesn't "return the wrong value"), so it earns a different, equally rigorous but non-redundant discipline.

### IX. Bilingual and Theme-Adaptive by Default
Testo MUST support Arabic and English, and MUST support both a light and a dark theme, as first-class capabilities built into every feature from the start — never retrofitted. No user-facing text MUST be hardcoded in a single language inside components or markup; all copy MUST be sourced through a translation/content layer covering both languages. Layouts MUST render correctly in both RTL (Arabic) and LTR (English), including mirrored alignment, spacing, and direction-sensitive iconography. Every component and screen MUST be styled so it is correct in both light and dark themes; colors and imagery MUST NOT be hardcoded in a way that breaks under either theme. A user's language and theme preference MUST persist at least per session. A feature is not complete if it only works correctly in one language or one theme. **Rationale:** Testo's students are Arabic speakers who also work daily in English technical terminology, so both languages are genuinely needed; retrofitting RTL and dark-mode-safe styling after screens are built is expensive and produces visible layout bugs across the whole product.

### X. Automated Grading Integrity, Auditability, and Adversarial Resistance
Essay/free-text questions are graded automatically by a server-side grading mechanism — currently semantic-similarity scoring against reference answers, with a documented future path to an AI/LLM fallback for low-confidence cases — with no routine human review before a grade is finalized (Principle VII). This automation, regardless of which specific mechanism computes the score, is only acceptable under the following non-negotiable guarantees:

- **Untrusted content, not instructions:** a student's submitted answer text MUST always be treated as content to be evaluated, never as a control input to the grading mechanism. Where the mechanism involves an LLM/prompt, student text MUST be structurally isolated from system/rubric instructions so embedded text cannot override the grading criteria (Principle II). Where the mechanism is non-generative (e.g. embedding similarity), this guarantee is satisfied by construction, since there is no instruction channel to hijack — but any future change to the mechanism MUST be re-evaluated against this guarantee before shipping.
- **Determinism and consistency:** grading the same answer against the same reference/rubric and the same model version MUST produce the same score every time. Any change to the underlying model, reference answers, or scoring configuration MUST be versioned so past grades remain explainable against the configuration that actually produced them.
- **No single point of comparison:** grading an essay answer against a single fixed reference answer is not sufficient, since a correct answer can be phrased in more than one valid way. The grading design MUST account for multiple valid phrasings of a correct answer rather than penalizing correct-but-differently-worded responses.
- **Calibration before real use:** any similarity threshold, cutoff, or scoring boundary used to convert a raw score into a grade MUST be calibrated against a representative sample of real or realistic answers before it is used to grade a real student's exam — never shipped as an untested default.
- **Advisory flags are audit-only, never a hidden gate:** the system MAY compute heuristic warning signals (e.g. a likely negation/contradiction between a student's answer and the reference, or a likely keyword-stuffing pattern) to support later review. These flags MUST be logged and MUST NOT block, delay, or alter automatic grade finalization — introducing a silent human-review step for flagged answers would contradict the fully-automatic grading decision (Principle VII) and MUST NOT happen. Flags exist solely so a later dispute or audit has more to go on than a bare score.
- **Full audit trail:** every automated grading pass and its result MUST be logged — the exact answer text graded, which reference answer(s)/rubric and model version were used, the raw score, any advisory flags raised, and a timestamp — so a grade can be reviewed or disputed after the fact, even though it was not reviewed before being finalized.
- **No silent failure:** if a grading pass fails or times out for any reason, the attempt MUST NOT be left silently ungraded. A bounded retry mechanism MUST run, following the same logged/retried pattern as Principle V, and any attempt still stuck in a failed-grading state MUST be visible to the Admin.
- **Post-hoc override remains possible:** an Admin MUST retain the ability to review and override any automatically-assigned grade after the fact through a documented, audited action (via the `voided`/regrade path in Principle IV) — grading without pre-review does not mean a grade is permanently unchallengeable.

**Rationale:** removing human review before finalization raises the stakes of every other safeguard, regardless of whether the mechanism behind the score is an embedding model or an LLM. A single-reference, uncalibrated, unlogged, or silently-failing automated grading path would be worse than no automation at all; these guarantees are what make full automation defensible rather than reckless, and they are written to survive the grading mechanism changing under them.

## Security & Compliance Requirements

- Row-Level Security MUST be enabled by default on every table holding user or exam data; a table is not considered shippable without it.
- Every endpoint or function that returns exam questions to a student MUST exclude grading-criteria fields (MCQ `is_correct` and essay rubrics/model answers alike) at the query level (Principle II) — this is verified in code review, not assumed.
- No privileged credential (Supabase service-role key, a future AI/LLM provider key, or equivalent) may exist in any file under the frontend package or in any client-shipped bundle; this is checked by secret-scanning before merge.
- Attempt tokens MUST be generated with a cryptographically secure random source (e.g. UUID v4), never sequential or derived from predictable data.
- All time comparisons for exam start/end MUST use server time, never a value supplied by the client.
- Rate limiting MUST be applied to any endpoint that saves answers or submits an exam, to prevent scripted abuse of a single attempt.
- The automated grading mechanism (embedding similarity today, LLM fallback in future) MUST treat student-submitted text as content to be scored, never as a control input; where the mechanism is prompt-based this isolation MUST be covered by an adversarial test case (see Quality Gates below).
- Any similarity threshold or grading cutoff MUST be calibrated against a representative answer sample before use on real student grades, and the calibration basis MUST be recorded (Principle X).
- Any paid inference/API cost introduced by the grading mechanism (e.g. a future LLM fallback) MUST be estimated per exam before publishing and tracked against actuals, alongside the existing email-cap tracking (Principle VI); Phase 1's local embedding inference has no such per-call cost to track.

## Quality Gates & Definition of Done

- A pull request MUST NOT merge unless its logic tests were written before its implementation, per Principle VIII, and CI proves this by running the full suite green.
- Any pull request that adds or changes a Row-Level Security policy MUST include at least one test proving denial of unauthorized access.
- Any pull request that adds or changes a themed/directional UI component MUST include passing Visual Regression Testing snapshots covering Arabic/RTL, English/LTR, light, and dark renderings before merge (Principles VIII & IX).
- Any pull request touching automated essay grading (reference-answer comparison, scoring logic, or any future prompt construction) MUST include tests proving grading is deterministic and, where prompt-based, that a prompt-injection-style answer cannot alter the assigned score or bypass the rubric (Principle X).
- Any pull request that adds or changes an advisory grading flag (e.g. negation or keyword-stuffing detection) MUST prove the flag is logged only and cannot delay, block, or alter automatic grade finalization (Principle X).
- Every `plan.md` MUST include an explicit Constitution Check confirming alignment with all principles above before `/speckit.tasks` generates implementation tasks; any necessary deviation MUST be documented with written justification in that plan, never silently implemented.
- A feature MUST NOT be marked complete if it depends on a client-side-only guarantee for anything covered by Principles I, II, or IV, or on an unlogged/unretried automated grading call for anything covered by Principle X.

## Governance

- **Authority:** This constitution supersedes any conflicting convention, prior document, or informal practice. Where `spec.md`, `plan.md`, or `tasks.md` conflict with this document, this document wins unless the constitution itself is formally amended.
- **Amendment authority:** Any developer on the project MAY propose and ratify an amendment — there is no single gatekeeper. This trust is paired with the amendment procedure below: authority to amend is not authority to edit silently.
- **Amendment procedure:** Changes MUST be made deliberately via the `/speckit.constitution` workflow (or an equivalent explicit review), never as a side effect of writing a spec or plan, and never as an uncommented inline edit. Each amendment MUST update `Last Amended`, bump the version per the policy below, and state which principle changed and why.
- **Versioning policy (semantic versioning):** MAJOR — a principle is removed or redefined in a way incompatible with prior specs/plans. MINOR — a new principle or section is added, or existing guidance is materially expanded. PATCH — wording clarifications or non-semantic refinements.
- **Conflicting amendments:** if two developers propose conflicting amendments, the conflict is resolved by discussion among the project's developers before either is merged — an amendment is never force-merged over an open objection.
- **Compliance review:** every `plan.md` MUST pass the Constitution Check gate (see Quality Gates above) before implementation tasks are generated.

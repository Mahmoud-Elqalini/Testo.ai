# Data Model: Group Invitation Codes

## Existing Entities Used

### Group (`public.groups`)

The existing group remains owned by one Admin. An invitation references exactly one group. Ownership is checked against the current authenticated Admin on every management operation; the redeeming Student cannot provide or change a group identifier.

### Group Membership (`public.group_students`)

The existing `(group_id, student_id)` primary key guarantees one membership per pair. Student redemption inserts into this table inside the database transaction. The existing insert trigger creates a pending exam attempt when a group permission applies to an already-started exam.

## New Entities

### Group Invitation (`private.group_invitations`)

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | Primary key, generated by database |
| `group_id` | uuid | Required FK to `public.groups`, cascade on group deletion, unique (at most one current invitation record per group) |
| `code_hash` | bytea | Required unique SHA-256 digest of a 128-bit random code; never returned to API clients |
| `created_by` | uuid | Required FK to `public.profiles`; must equal the Admin who owns the group when managed |
| `created_at` | timestamptz | Required; set by database on create and rotation |
| `expires_at` | timestamptz | Required; 30 days after create or rotation |
| `revoked_at` | timestamptz | Nullable; set when the owning Admin revokes the invitation |

The usable code exists only in the create/rotate RPC response. It is not stored in the row, included in the status RPC, or recoverable after that response. Rotation replaces `code_hash`, resets expiry/revocation, and invalidates the former code in the same transaction.

RLS is enabled. The `private` schema is not exposed through the Supabase Data API, application roles receive no table privileges, and all invitation access goes through narrowly granted functions that enforce Admin ownership or Student role. No client-facing function returns `code_hash`.

### Redemption Throttle (`private.group_invitation_redemption_limits`)

| Field | Type | Rules |
|---|---|---|
| `student_id` | uuid | Primary key and FK to `public.profiles`, cascade on account deletion |
| `window_started_at` | timestamptz | Start of the current 15-minute failed-redemption window |
| `failed_attempts` | integer | Nonnegative count for that window |
| `blocked_until` | timestamptz | Nullable; set once five failed attempts are reached |

One row per Student is updated atomically during failed redemption. Successful redemption clears the current failure count. The table contains no submitted code and no IP address.

RLS is enabled with no direct policies or API grants. It is readable and writable only by the restricted database function owner.

## State and Transaction Rules

- Active: `revoked_at IS NULL AND expires_at > now()`.
- Rotated: same row receives a new code digest, new `created_at`/`expires_at`, and `revoked_at = NULL`; old code can no longer match.
- Revoked: `revoked_at` is set. Existing memberships remain untouched.
- Expired: `expires_at <= now()`. Redemption is denied; Admin may rotate it to issue a new code.
- Redemption validates auth, Student role, throttle, digest, and invitation state; inserts membership with conflict-safe semantics; and clears throttle state on success in one transaction. Existing membership triggers remain responsible for pending exam attempts.
- Rotation and redemption lock the invitation row while validating/updating it, preventing stale concurrent redemption from succeeding after rotation commits.

# Implementation Plan: Unified Identity and Relationship-Based Access

**Branch**: `007-unified-identity` | **Date**: 2026-11-05 | **Spec**: [spec.md](spec.md)

## Summary

Replace fixed student/admin authorization with authenticated identity plus resource ownership and group membership/participation. Freeze and execute a migration-derived security baseline before changing authorization, install all replacement checks before dropping role state, preserve group-based exam access, and consolidate the signed-in experience into one bilingual dashboard. The migration sequence begins at `0014`; its final authorization step removes `profiles.role` and its mirror only after the after-state checks pass.

## Technical Context

**Language/Version**: TypeScript (repository application), SQL/PostgreSQL (Supabase migrations), Deno TypeScript (Edge Functions).
**Primary Dependencies**: Next.js App Router, React, Supabase JS v2, local Supabase CLI, existing i18n/theme providers.
**Storage**: Supabase PostgreSQL with RLS; no course data or storage work in 007.
**Testing**: Existing project test tooling plus SQL/pgTAP or scripts against local Supabase; use the identical frozen allow/deny cases before and after. UI visual regression in EN/LTR, AR/RTL, light and dark as required by Constitution VIII/IX.
**Target Platform**: Local Supabase and web app; no staging project.
**Project Type**: Next.js web application with Supabase backend and Edge Functions.
**Performance Goals**: Preserve current request flows; lookup rate limits and response normalization must not make account-existence timing distinguishable.
**Constraints**: No production users/data; local test data may reset. Do not start implementation until the baseline inventory and before-suite results are frozen and recorded. Role columns/helpers remain until all replacement checks are installed and verified.
**Scale/Scope**: Existing groups, exams, profiles, exam permissions, attempts, answers, invitation flow and role-separated UI routes; courses are out of scope.

## Constitution Check

- **I–II, IV–X**: Preserve existing exam privacy, attempt lifecycle, grading integrity, audit, rate limiting, bilingual/theme requirements and test-first discipline. Question delivery remains a safe projection and never returns correct-choice/reference-answer fields before authorized result access.
- **III, XII**: Pass only if no migration commits an intermediate weaker state; each authorization migration has security tests run before and after; every old role/admin check has a documented equally-or-more-restrictive replacement; identity comes from `auth.uid()` and verified ownership/membership, not client claims.
- **XI**: Plan uses the existing SQL/RLS, service, Edge Function, route, and translation boundaries; no speculative repository/framework layer is proposed. See Maintainability Review.
- **XIII**: No course tables/media are included; the future 008 course design must apply its protected-content requirements.
- **Gate**: PASS with mandatory baseline-first and migration-order conditions. Implementation must stop if the frozen inventory does not match the applied local schema or any baseline case cannot be reproduced.

## Maintainability and Design Review

- **Responsibilities and boundaries**: PostgreSQL owns authorization and relationship integrity; narrowly scoped server functions expose profile projections; Edge Functions authenticate attempt operations and pass verified identity; existing services adapt to new data names; the dashboard composes existing learning/teaching data and route destinations.
- **SOLID review**: Each server function has one disclosure/action purpose. Group membership and exam access remain separate relationships. UI does not decide authorization. Data access depends on Supabase contracts already in use. Avoid combining email lookup with participant listing because they have different disclosure rules.
- **Dependency direction**: UI → existing service modules → authenticated Supabase RPC/RLS/Edge endpoints → database. Database checks derive identity from `auth.uid()` and join resource ownership or membership. Edge operations use authenticated user identity and never authorize from request-supplied user IDs.
- **Patterns and alternatives**: Two explicit SECURITY DEFINER projections are required: associated-participant list (name+email) and exact lookup (id+name, never email). This split directly enforces FR-008/FR-009; one generic profile/search endpoint would make accidental over-disclosure easier. No new general repository or policy abstraction is justified.
- **Scope and complexity**: Keep 007 limited to groups, exams, profiles and dashboard. Group invitations remain the supported join path; exam invitation is deferred. Preserve testable legacy domain behavior while deleting role-specific branches.

## Authorization and Attack-Surface Decisions

- **Lookup enumeration**: exact email only; caller supplies context id but database verifies current ownership. Return only id/name for already-associated people; return identical empty shape for missing/unassociated; rate-limit by `(auth.uid(), context_id)` and normalize execution path to avoid timing signals. No email is returned.
- **Self-exam**: pending attempt creation and start both check `attempt.student_id=auth.uid()` and `exam.owner_id <> auth.uid()`; enforce in the database path so stale links and direct RPC/API calls fail. No question projection for owner.
- **Self-join**: invitation redemption binds new membership to `auth.uid()` and checks `group.owner_id <> auth.uid()` at insertion. A DB trigger/constraint protects any alternate insert path.
- **Profile enumeration**: remove broad authenticated profile reads; self-only profile access stays self-only. Owner projection requires an exact owned context and active relationship and returns only columns `id/full_name/email`; no preference fields. Recheck association on every call so removal immediately ends visibility.
- **Participant email visibility**: owner participant-list endpoint returns name+email only for members/permission holders/attempt holders in that owner's context. Participant endpoints never return owner or peer email. Lookup endpoint is separate and returns id+name only. Separate allow/deny and shape-leak tests are mandatory.
- **Client-supplied values**: no `student_id`, owner id, role, membership, permission or attempt owner field from a request can confer rights. Inserts derive identities from auth; target context ownership and relationship are checked server-side. RLS WITH CHECK clauses reject spoofed owners.
- **Correct answers**: RLS never grants participants direct question SELECT. The safe question function excludes `correct_choice` and `reference_answers`; only the completed-result function and exam owner review path may reveal authorized grading data. Tests inspect both column grants and JSON payloads.

## Migration Order (starting at 0014)

All work is on local Supabase. Each authorization migration ships with a test change written first and passes the frozen before/after suite. Apply each migration and test its intermediate state before proceeding. Do not remove any role source until the last step.

1. **Pre-migration freeze (no schema change)**: inventory all function/policy/trigger/Edge dependencies from 0001–0013 and local `pg_catalog`; commit the matrix, fixtures, exact cases and results. Run current-state baseline suite and save machine-readable results. No authorization edit precedes this gate.
2. **0014, additive owner model**: add nullable `owner_id` to `groups` and `exams`, backfill from `admin_id`, add FKs/indexes, and add owner-oriented helper functions. Keep all existing authorization checks. Install a BEFORE INSERT OR UPDATE trigger on each table enforcing `owner_id = admin_id`: on insert, fill either missing value from the other; on update, if exactly one changes, mirror that value to the other; if both are set and diverge, raise and reject the write. Existing RLS checks continue to bind `admin_id` to `auth.uid()` during this bridge, so an authenticated caller cannot transfer ownership by changing both values. Test insert, either-column update, divergent dual update, and spoofed transfer for both tables.
3. **0015, additive preparation only**: create replacement helper definitions and test fixtures/harness without switching policies, removing direct permission rows, changing group membership write paths, or disabling role-based functions. All old policies and functions remain active. Run intermediate deny/allow checks after this migration; expected results match the frozen baseline.
4. **0016, additive profile functions only**: add the two new server-side projections (FR-008 associated list and FR-009 associated lookup) and their rate-limit support, but do not route clients to them or drop/replace old profile/search functions or policies yet. ### Critical test families

- Every row in the 27-policy table and every function/trigger/Edge item has at least one successful allowed case and one denied case before and after.
- Owner A can manage only A's groups/exams; Owner B and U cannot read, change, or delete A resources, memberships, permissions, attempts, answers, invitations or private profiles.
- P can access only own permitted group/exam/attempt; U cannot imitate P by supplying P's id, attempt id, owner id, role or group id in JSON/SQL RPC parameters.
- Owner A cannot join A's group, create/start an attempt on A's exam, or fetch questions/results for a self-owned exam. Test invitation, direct table mutation, stale attempt URL, Edge call and RPC paths.
- Membership creation is possible only through `redeem_group_invitation`: revoke client INSERT/UPDATE privileges and remove permissive insert/update RLS policies. Direct PostgREST INSERT and UPDATE as owner, participant, unrelated user and anon are denied; invitation redemption for its authenticated caller is the sole allow case. Audit all `INSERT INTO group_students` references in migrations/functions/application code; pending-attempt triggers only create attempts and do not create memberships.
- Unauthenticated direct REST/RPC/Edge requests return no protected rows and cannot mutate protected state.
- FR-008 group participant list returns current group members only. FR-008 exam participant list returns the union of (a) current members of groups linked to that exam and (b) accounts with an existing `exam_attempts` row for that exam. A participant removed from a linked group remains visible to the exam owner for grade review while the attempt row exists; removal from the group immediately removes them from group participant lists. Deleting the attempt removes exam-list visibility. In all cases return only name+email to the owning context; participants never see owner or peer email.
- FR-009 lookup returns id+name only for an associated exact match; arbitrary and malformed emails never indicate existence; unassociated and nonexistent have identical status/JSON shape; per requester and context throttles are isolated and enforced. Lookup and list tests are separate.
- Attempt question response has no `correct_choice`, `reference_answers`, grading rubric, or answer key. Open attempts/results cannot reveal answers; own completed result and exam-owner review retain only their authorized results.
- Void and grade override: relevant exam owner allow; unrelated owner/participant deny; audit record identity derives from auth.uid.
- For 0014, 0015 and 0016, frozen allow/deny cases prove old security remains active and the owner mirror remains equal. The full replacement set is tested and committed atomically in 0017; rerun the full matrix after 0017, 0018, 0019, 0020 and 0021. Migration tests assert role artifacts exist before 0021 and are dropped only in 0021.
- Catalog audit enumerates every `SECURITY DEFINER` function across migrations and final database: fixed non-user-controlled `search_path`, schema-qualified references, and explicit execution grants. Existing user-callable functions using `SET search_path = public, pg_temp` (attempt functions, result lookup, and expiry sweep) must be reviewed and moved to an empty/otherwise fixed safe path with qualified references. Every user-callable function must check `auth.uid()` and the relevant relationship. The current 0008–0009 attempt RPCs instead trust a `p_student_id` supplied by the Edge Function while service-role-only; the plan replaces that with authenticated-JWT RPC calls so the database can verify `auth.uid()` directly. Trigger/cron/internal helpers that cannot meaningfully authenticate an end user (`fn_create_profile_on_signup`, pending-attempt/immutability/protection triggers, expired-attempt sweep, and private code/hash helpers) must instead be proven non-callable by `anon`/`authenticated`, invocable only from trusted trigger/scheduler/internal context, and free of caller-controlled identity. Remove unneeded SECURITY DEFINER attributes/grants where possible. This distinction must be documented per function in the frozen catalog audit; it is not an authorization exception for user-facing RPCs.
